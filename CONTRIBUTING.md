# Contributing to PlainX Editor

Thanks for helping make PlainX better. This guide keeps contributions fast to
review and safe for users' data.

## Getting started

```bash
git clone https://github.com/your-org/plainx-editor.git
cd plainx-editor
Scripts/bootstrap.sh      # build the app
Scripts/test.sh           # run unit + integration tests
```

Open `PlainX.xcodeproj` for development. The Xcode project is generated by
`Scripts/generate-project.py`; source files inside `PlainX/`, `PlainXTests/`,
and `PlainXUITests/` are picked up automatically from the file system, so you
normally do not need to regenerate the project when adding files. Regenerate it
if you change vendored sources or target settings.

## Project layout

See [docs/architecture.md](docs/architecture.md). The important boundaries:

- `PlainX/Editor` — Scintilla bridge and editor panes. Raw Scintilla message IDs
  live only in `ScintillaFacade.swift`.
- `PlainX/Documents` — document model, encoding/EOL handling, safe file IO,
  sessions, recovery.
- `PlainX/LargeFile` — memory-mapped large-file engine and viewer.
- `PlainX/Features` — search, search-in-files, diff, macros, transforms,
  command palette.
- `PlainX/Commands` — the command registry that drives menus, the palette, and
  macros. Add features as commands wherever possible.
- `Vendor/` — pinned Scintilla/Lexilla sources. Treat as read-only.

## Non-negotiable rules

1. **Data safety first.** Saves are atomic and never overwrite external changes
   without asking. Never break this for speed.
2. **Stay native and lightweight.** No Electron/web runtimes, no new large
   dependencies, no telemetry. New dependencies must be justified in the PR.
3. **No secrets in the repo.** Signing identities and notarization credentials
   live in the keychain or GitHub Secrets.
4. **Don't log user content.** Never log document text, selections, clipboard
   contents, or file contents.
5. **Tests.** New pure logic gets unit tests; file IO and search changes get
   integration tests. Aim for deterministic tests using generated fixtures,
   not committed large binaries.

## Code style

- Swift 5 language mode, AppKit-first. Keep view controllers thin; put logic in
  services so it can be tested without a GUI.
- Prefer value types and structured errors with user-readable messages.
- Avoid force unwraps in file/parsing paths.
- UI strings are currently English; keep sentences whole (no fragment
  concatenation) so future localization stays possible.
- Match the existing naming and file organization.

## Pull requests

- Keep PRs focused; small PRs review quickly.
- Fill in the PR template, including how you tested the change.
- Update `CHANGELOG.md` for user-visible changes.
- CI must pass: Debug build, unit/integration tests, and a Universal 2 Release
  build.

## Reporting bugs

Use the bug report template and include the Tools → Copy Diagnostics output
when relevant. Attach minimal, non-sensitive sample files only.
