# Performance

PlainX Editor is developed against explicit performance budgets. This page
records measured results; it is updated with fresh numbers from
`Scripts/benchmark.sh` (developer-only tooling; nothing is collected remotely).

## How to reproduce

```bash
Scripts/benchmark.sh          # fixtures + Release build + all measurements
Scripts/benchmark.sh --quick  # skips the 1 GB fixture
```

The benchmark generates deterministic fixtures (1 MB text, 20 MB log,
100 MB log, 1 GB log) under `~/Library/Developer/PlainXBuild/benchmark-fixtures`,
builds a Release app, and measures launch time, resident memory (in-process
`task_info` plus `/usr/bin/time -l`), Large File Mode indexing, and streaming
search throughput. The 1 GB stress fixture is skipped automatically when free
disk space is below ~1.3 GB.

## Budgets (targets from the engineering specification)

| Scenario | Target RSS |
|---|---:|
| New blank window | ≤ 60 MB preferred, ≤ 90 MB hard review |
| 1 MB plain text | ≤ 100 MB |
| 20 MB log, regular mode | ≤ 160 MB |
| 100 MB regular text | ≤ 300 MB, otherwise Large File Mode |
| 1 GB file, Large File Mode | ≤ 200 MB typical working set |

Launch targets (warm cache): UI visible ≤ 500 ms preferred, usable editor
≤ 800 ms. Package targets: DMG ≤ 40 MB, app bundle ≤ 80 MB (Universal 2).

## Measured results

### 2026-10-12 — v1.0.0 (Apple Silicon / arm64, Release)

- Machine: Apple Silicon Mac (arm64), macOS 27.0
- Build: Release, native architecture, warm filesystem cache
- Fixtures: generated by `Scripts/benchmark.sh`

| Measurement | Result | Budget | Status |
|---|---:|---:|---|
| Launch (app setup → finished launching) | 115–125 ms | ≤ 500 ms | Pass |
| Blank window RSS (open / peak) | 87 MB / 103 MB | ≤ 90 MB hard | Pass (above 60 MB preferred) |
| 1 MB text open | 19 ms | – | Pass |
| 1 MB text RSS (open / peak) | 94 MB / 125 MB | ≤ 100 MB | Pass |
| 20 MB log open, regular mode | 263 ms | – | Pass |
| 20 MB log RSS (open / peak) | 196 MB / 227 MB | ≤ 160 MB | Over budget (see notes) |
| 100 MB log, Large File Mode index | 245 ms | – | Pass |
| 100 MB log RSS (index / peak) | 150 MB / 171 MB | – | Pass |
| 1 GB log, Large File Mode index (13,176,353 lines) | 2.0 s | – | Pass |
| 1 GB log RSS (index / peak) | 150 MB / 171 MB | ≤ 200 MB | Pass |
| 1 GB mmap open (no index) | 4 ms | – | Pass |
| Streaming search, full 1 GB scan (rare pattern) | 627 MB/s (1.6 s) | – | Pass |
| Streaming search, dense matches (100k result cap) | 2.26 GB/s effective (0.45 s) | – | Pass |
| Search RSS during/after full scan | 82–92 MB | – | Pass |

### Large File Mode memory strategy (why these numbers hold)

- The file is memory-mapped read-only, but indexing and search use bounded
  `pread` windows into a reusable buffer, so scanning a 1 GB file does not
  accumulate resident file-backed pages. RSS stays flat at ~80–150 MB while
  indexing 13 million lines.
- Exact line resolution uses sparse checkpoints (one per 1 MB) plus a bounded
  local scan, so the index is kilobytes, not one entry per line.
- The viewer renders only the visible window (hard-capped per frame), so
  scrolling a 20-million-point document does not allocate for the whole
  surface.
- Search literal matching runs on bytes with an ASCII-aware fast path; a
  `String` is only allocated for lines that actually match.

## Known gaps

- **Blank-window RSS (82–98 MB)** is around the 90 MB hard-review threshold
  and above the 60 MB preferred target. Measured evidence (2026-10-13):
  an untitled editor window sits at 82 MB, while the Welcome screen (which
  creates **no** Scintilla view at all) measures 97–98 MB warm and cold.
  The baseline is therefore AppKit/framework loading plus view/text caches,
  not the editor engine or document buffers. Reducing it requires trimming
  the window content and framework footprint, tracked for a future release.
- **20 MB regular-mode open (196 MB)** exceeds the 160 MB target: the regular
  path holds the decoded `String` plus Scintilla's UTF-8 buffer, style bytes,
  and line layout. Files at or above the Large File threshold (default 64 MB)
  avoid this entirely. Users can lower the threshold in Settings → Large Files;
  the trade-off is syntax highlighting on mid-size files.
- Regular-mode opens of files just below the threshold still peak at roughly
  6× file size transiently; the threshold default was selected so 100 MB files
  take the Large File path.

## Package size

Recorded from `Scripts/make-universal.sh` and `Scripts/package-dmg.sh`:

| Artifact | Size | Budget |
|---|---:|---:|
| `PlainX.app` (Universal 2, Release) | 8.7 MB | ≤ 80 MB |
| `PlainX-Editor-v1.0.0-universal.dmg` | 4.0 MB | ≤ 40 MB |

Both are comfortably inside budget: the app bundles only Scintilla/Lexilla
(curated lexer set), the compiled Swift code, and asset catalogs. The DMG
contains the app plus an `/Applications` symlink.

## Leak pass

Run with a 100 MB file open in Large File Mode and ~12 s of idle time
(`leaks <pid>` on the Release build):

```
Process: 104,926 nodes malloced for 12,371 KB
417 leaks for 20,016 total leaked bytes
```

All 417 reported leaks (20 KB) are root cycles inside Apple's
`com.apple.linkd.autoShortcut` XPC connection (the same daemon that logs
"connection to service named com.apple.linkd.autoShortcut" at launch). No
leaks were attributed to PlainX's own code. This is re-checked each release
with `Scripts/benchmark.sh` plus a manual `leaks` run.

## Methodology notes

- "Open/RSS" is sampled in-process immediately after the tab is ready;
  "peak" is the maximum resident set reported by `/usr/bin/time -l` across the
  run.
- Large File Mode numbers include mapped pages that happen to be resident at
  measurement time; the OS and the app's explicit buffer design keep this
  bounded regardless of file size.
- Launch timing measures from the process entry point (`main.swift`) to
  `applicationDidFinishLaunching` returning, on a warm cache.
- No user telemetry is involved anywhere in this process.
